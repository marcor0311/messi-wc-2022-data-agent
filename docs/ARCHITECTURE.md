# Messi Football Data Agent

The product centers on Lionel Messi at Qatar 2022. Other entities provide comparisons and match context. `/agent` is the new workspace; the museum remains independent.

## Data discovery and preparation

`scripts/discover_gold.py` verifies every manifest checksum, profiles all eleven Gold JSONL tables and every top-level/metric column, records types/nulls/ranges/categorical values, and builds an indexed read-only SQLite serving database. The newest local Gold manifest is selected unless `--gold` pins a folder. The two local Gold versions have identical dataset file checksums but different definitions hashes; the active load is recorded in generated documentation. Metric dictionaries are flattened without altering original Gold. Tactical player arrays and quality/context records retain JSON structure.

Run discovery and `scripts/argentina_match_summaries.py` before a demo, never inside a conversation. The latter builds `data/agent/argentina_matches.json` from the matching Silver event and lineup snapshots; `match_result` and `lineup_story` require this companion next to the serving database. It carries scores, cards, substitutions, shootouts, jersey numbers and position spells. Use its `--silver`, `--roster` and `--output` options to pin inputs and serving location. Neither preparation script modifies chat history or credentials.

The immutable snapshot, indexed filters, existing Gold player/team match aggregates and passing connections do the heavy work before questions. Spatial bins are precomputed at match/team/player/type/period dimensions. Compatible heatmaps use those caches; novel extra filters use bounded raw aggregations. The serving database checksum and cache version are verified before loading. The full ETL is never invoked by a request.

## Tools and model

`find_entities` resolves real IDs. `describe_data` supplies schemas and definitions. `query_gold` accepts a Pydantic contract, validates every identifier against the discovered schema and binds every value as a SQL parameter. The LLM cannot issue SQL, scripts, frontend code or unrestricted filesystem operations. Limits bound filters, groups, metrics, rows and SQLite instructions. Nulls, unknown outcomes, count scopes, truncation and provenance are explicit. Sparse action metrics follow Gold's zero-contribution convention; raw missing coordinates remain null. Ratios recompute numerator/denominator sums. Direct shot involvement cannot be summed across players.

The turn runs as a LangGraph `StateGraph` in `apps/api/src/app/agent/runtime.py`: a `model` node calls Responses, a conditional edge ends the turn on a text answer or routes tool calls to a `tools` node, and `tools` returns to `model`. Inputs, visualizations and trace accumulate in the graph state. The model may request several tools in one step (`parallel_tool_calls`), and the `tools` node runs them together. Entity IDs (matches, teams, players), metric definitions and limitations travel in the instructions, built once per process with the compiled graph, so `find_entities` and `describe_data` are only fallbacks. The account credentials travel in the run config, never in graph state. Presentation rules that must always hold are enforced in code, not left to the model: comparisons between players or teams whose data covers different matches are rejected with a repair hint (filter to shared matches), one player's given-pass network always comes with his received-pass network, and a stat card that only repeats a total already drawn by another chart of the answer is dropped. The loop uses the authenticated account catalog and its selected model, public `https://api.openai.com/v1/responses`, `store:false` and `stream:true`. It accepts results only after `response.completed`; failed, incomplete and interrupted streams fail the turn. Multiple tool calls can discover entities, compare scopes and construct multiple registry visualizations. Conversation history includes previous tool evidence, with a bounded recent context window. Tool errors are returned to the model for repair. A per-turn budget of model calls (10, plus 2 for each chart produced, capped at 20) and 100 persisted turns bound a session. No hardcoded question routing or answer cache is used. This is the only agent: the earlier bounded-intent prototype (its own graph and `/api/conversations` endpoints) was removed.

## Authentication and local security

Official SIWC dynamic public-client registration, stable UUID host, fresh state/nonce/PKCE, loopback callback, issued client ID reuse, signed JWKS ID-token validation (issuer, audience, expiry, nonce), direct-plan scope check, and serialized refresh rotation are implemented. OAuth state is saved atomically in the root `.env` under `AGENT_AUTH_STATE_B64`, with mode `0600`; existing local state migrates from `data/agent/credentials.json` on first startup. Tokens are never returned to frontend JavaScript. Saved registrations are separate by client ID and verified subject. API access logging is disabled in the documented commands to keep authorization codes out of logs. No API key and no unofficial ChatGPT backend endpoint exists.

Local-only service: bind to `127.0.0.1`. One API worker owns refreshes and credential writes. `AGENT_CALLBACK` and `AGENT_WEB_ORIGIN` must match the selected loopback ports. Local HTTP cookies are intentionally not Secure; remote deployment requires a separate security design. Browser mutation origins are checked. Deterministic Gold exploration is public to the local process; authenticated chat/history are owner scoped.

## Visualization contracts

A server view registry validates compatible source datasets and forbids custom field projections for visual views. The frontend registry renders tables, grouped bars, chronological metric trends, event maps, binned event heatmaps, completed-pass networks, schematic declared starting XIs, created-shot chains, tactical lineup changes and match-result timelines. Every result includes an accessible exact-data table and reproducible query/source hashes. Filters and interactive data selection refine interpretation. Starting XIs and tactical stories use labelled team tabs and a schematic pitch for the selected team. These positions are schematic and never presented as tracking coordinates.

## Chart selection, presentation and audiences

The model instructions map the user's intent to a view (events on the pitch, zones, headline numbers, comparison, evolution, partners, starting XI, chronology) and ask for a short human title per query and up to four complementary views per answer. An event listing requested as a table always gets a companion pitch map, added by the server. Every result reaches the model with a names lookup for the player, team and match IDs in its rows.

The frontend renders totals as stat cards, comparisons and evolutions as one panel per metric (never two scales on one axis), shots with inspectable xG, destinations and outcome markers, pass networks with one node per player at the mean location of their passes, and a minute strip above the event list. Each renderer distinguishes the focus player and comparison series; names and exact values remain available without relying on color. Gold keeps provider values in English and full legal names; the interface shows Spanish labels and the provider's short names from the Silver roster. Each view keeps hover and keyboard detail, an exact-data table and the reproducible query.

The composer selects the account model per question. The current route always uses the analyst audience; `audience` remains accepted only for older clients. The `/agent` route mounts `agent-propuesta/workspace.tsx`. The public tab currently presents the view catalog, while the deterministic query endpoint remains available.

## Verification boundaries

Deterministic Gold integration tests independently read raw JSONL and compare Messi totals, non-penalty shots, tournament metrics, opponent comparisons and both final starting XIs. Mocked tests cover model tool selection, follow-up evidence, signed identity validation, replay/expiry, logout and terminal streaming. Those tests do not prove live OAuth eligibility or live model quality. The live sign-in, catalog discovery and four real question/tool/visualization rounds are recorded in `VERIFICATION.md`.
